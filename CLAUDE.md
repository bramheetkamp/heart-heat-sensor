# CLAUDE.md

This file guides Claude Code (claude.ai/code) when working in this repository.

## What this is

**Pulse** (a.k.a. Heartrate) — a consumer-grade **iOS app + sync backend** for a
BLE wearable with a MAX30102 heart-rate sensor and dual temperature sensing,
targeting an **nRF52840 DK** running Nordic's standard `ble_app_hrs` firmware
(standard GATT: HR Measurement notify + Temperature Measurement notify).

**The hardware does not exist yet.** Everything works end-to-end against
simulated data via **Demo Mode**, which feeds synthetic measurements through the
*same* BLE pipeline as a real device — so the UI, parsers, and warnings engine
see no difference. Swap in the real device later by turning Demo Mode off.

> Note: this is the *companion* project to `../BodyTempSensor` (the actual
> nRF54L15 sensor firmware). This repo is the phone app + cloud side.

## Build / run / test

### Backend (from `backend/`)
```bash
npm install
cp .env.example .env        # set JWT_SECRET at minimum
npm run dev                 # tsx watch, http://localhost:3100
npm run seed                # test@example.com / password123 + 35 days of data
npm test                    # vitest, 50 tests, in-process via Fastify inject() — no port
docker-compose up           # alternative to npm run dev
```

### iOS (from `ios/`)
```bash
bash generate_project.sh    # installs XcodeGen if missing, generates HeartRate.xcodeproj
open HeartRate.xcodeproj    # select an iPhone simulator, ⌘R
xcodebuild test -project HeartRate.xcodeproj -scheme HeartRate \
  -destination 'platform=iOS Simulator,name=iPhone 16' 2>&1 | xcpretty
```

- The Xcode project is **generated by XcodeGen from `ios/project.yml`** — it is
  *not* checked in as source of truth. Edit `project.yml`, then re-run
  `generate_project.sh`. Never hand-edit `HeartRate.xcodeproj`.
- **`Info.plist` is hand-maintained** (BLE usage strings, `heartrate://` URL
  scheme, background modes, ATS). Do NOT add an `info:` block to `project.yml` —
  it would make XcodeGen overwrite the curated file. The target points at it via
  `INFOPLIST_FILE`.
- iOS 17 deployment target, Swift 5.9, iPhone-only. Set `DEVELOPMENT_TEAM` in
  `project.yml` to run on a physical device.

## iOS architecture & data flow

```
BLE transport ──► BLEService ──► (parsers already applied) ──► DataStore (SwiftData)
   (real or mock)      │                                            │
                       │ persists a Reading every ~5 s              ▼
                       ▼                                      WarningsEngine
              @Published live HR/temp ───────────────────────────► Views
```

- **`AppEnvironment`** is the central DI container (created in `HeartRateApp`,
  injected as an `@EnvironmentObject`). It owns `BLEService`, `DataStore`,
  `DemoModeService`, `SyncService`, `NotificationService`, and `AppRouter`, and
  publishes `isDemoMode` and `appearance` (defaults to dark) to `UserDefaults`.
- **BLE is behind a protocol** (`BLETransportProtocol`) so `CoreBluetoothTransport`
  (real) and `MockBLETransport` (simulated) are interchangeable. `AppEnvironment`
  picks the mock **on the simulator or when Demo Mode is on**, else CoreBluetooth.
- **`BLEService`** subscribes to the transport's Combine publishers
  (`connectionStatePublisher`, `hrMeasurementPublisher`, `temperaturePublisher`,
  `edaPublisher`), exposes `@Published` live values, fires connection haptics, and
  — when given a `DataStore` — persists a combined `Reading` (latest HR + both
  temp sites + EDA) each time a `.core` temperature arrives (~5 s cadence).
  HR is **optional**: a temperature/EDA-only device (BodyTempSensor) still
  persists, with `activity = .unknown` when HR is absent (else HR ≥ 100 ⇒ `.active`).
  Old rows are pruned beyond ~180 days to bound growth.
- **Persistence is SwiftData** (`DataStore`, `@MainActor`): models `Reading` and
  `UserProfile`. Falls back to in-memory if the on-disk store fails to open.
- **Navigation** is `NavigationStack` bound to `AppRouter.path` (a
  `NavigationPath`) + a typed `AppRoute` enum, so every screen is addressable and
  deep-linkable. Sheets via `AppSheet` (`.onboarding`, `.scenarioPicker`).
- **`WarningsEngine`** is a pure `struct` with only `static` methods and no
  SwiftData dependency — fully unit-testable. See "Warnings engine" below.
- **Sync is additive and optional** — the app works 100% offline. `SyncService`
  talks to the backend (base URL from `API_BASE_URL` env or `http://localhost:3100`).

### Key iOS files
- `App/` — `HeartRateApp` (`@main`, `onOpenURL` deep-link entry), `AppEnvironment`, `RootView`
- `Navigation/` — `AppRouter` (push/sheet/`handle(url:)`), `AppRoute` (+ `HistoryMetric`, URL parser)

### BLE protocol details (must match firmware)

The app supports **two device profiles and auto-detects** which one a peripheral
implements — it scans for all known service UUIDs and subscribes to whatever it
finds. **Full contract: `docs/BLE_CONTRACT.md`** (the source of truth shared with
the `../BodyTempSensor` firmware).

- **Profile A — standard GATT.** Heart Rate `0x180D` / `0x2A37` (notify; flags
  bit0 = uint16 format, bits1–2 = sensor contact, bit3 = energy, bit4 = RR; RR in
  **1/1024 s** → seconds). Health Thermometer `0x1809` / `0x2A1C` (IEEE-11073
  32-bit FLOAT; Type field → `.skin`/`.core`; 2nd temp char ⇒ "Site 2").
- **Profile B — BodyTempSensor custom service** (`a0b40000-7e9c-4f1a-9a1e-7c0ffeed0001`,
  advertises name `BodyTempPoC`). Three notify chars, each a native little-endian
  `float32`: skin `…0001` (°C), core `…0002` (°C), EDA `…0003` (µS) — decoded by
  `BodyTempFrameParser`. **No heart rate** on this device. The app does *not* use
  the raw combined-frame char (`…0004`), only the scalars. The firmware advertises
  its 128-bit UUID in the **scan response** so the filtered scan can find it.
- `CoreBluetoothTransport` reconnect: **exponential backoff with jitter** (1 s base,
  30 s cap), a 10 s connect timeout, and a **direct reconnect to the last
  peripheral**. An explicit `disconnect()`/`stopScanning()` forgets that peripheral
  (so a later scan can pair a different device); a transient drop keeps it.

## Backend architecture

- **Fastify 4 + better-sqlite3**, ESM (`"type": "module"`, `.js` import
  extensions required even in TS source). Build with `tsc`, run with `tsx`.
- `buildServer(opts)` in `src/server.ts` constructs the app and is the seam used
  by tests (override `dbPath`, `jwtSecret`, rate limits, Apple JWKS). The file
  only calls `.listen()` when run directly.
- **Auth**: `@fastify/jwt`, bcrypt password hashing, plus **Sign in with Apple**
  with full RS256 JWKS verification (`iss`/`aud`/`exp`) in `services/appleAuth.ts`.
- **Rate limiting**: global 200 req/min backstop; tighter per-route overrides on
  auth and `/readings/batch`.
- **SQLite** (`src/db/index.ts`): WAL mode, foreign keys on. Tables `users`,
  `readings`, `warnings` (see schema in that file). `readings.rr_intervals` is a
  **JSON string of milliseconds**; `temp_site1` = core, `temp_site2` = skin (°C);
  `eda` in µS; `activity` is `'rest' | 'active' | 'sleep'`. New columns are added
  by the idempotent `migrate()` (run on every `createDatabase`), because
  `CREATE TABLE IF NOT EXISTS` never alters an existing table.
- **Routes** (`src/routes/`): `auth.ts`, `readings.ts`, `warnings.ts`,
  `wellknown.ts` (AASA for Universal Links). `POST /readings/batch` upserts up to
  1000 readings; `POST /warnings/recompute` re-runs the engine server-side.
- **Validation** with zod. `src/types.ts` is the shared row/DTO contract.

### API surface
`POST /auth/register`, `POST /auth/login`, `POST /auth/apple`,
`POST /readings/batch` (JWT), `GET /readings?from&to&limit` (JWT),
`GET /warnings` (JWT), `GET /warnings/:id` (JWT), `POST /warnings/recompute` (JWT),
`GET /.well-known/apple-app-site-association`, `GET /health`.

## Warnings engine (the core domain logic)

Three rules, implemented **twice** — `ios/.../Services/WarningsEngine.swift`
(client, realtime/offline) and `backend/src/services/warningsEngine.ts` (server,
recompute). Every warning carries trigger values + baseline values + a trend
array so the UI can show **why** it fired. Wellness framing only — no medical
diagnosis language.

| Rule | Fires when |
|---|---|
| **OVERHEATING** | core temp over the threshold (iOS: `profile.overheatingThreshold`, default 38.5 °C; backend: hard-coded 38.5), OR a rise > 1.0 °C within a 30-min window |
| **GETTING_SICK** | daily resting HR or temp elevated vs the 30-day rolling baseline (HR +5 bpm, temp +0.3 °C) on ≥ 2 days |
| **FATIGUE_RECOVERY** | 7-day resting HR elevated (iOS ≥ +8%, backend ≥ ×1.08) AND HRV (RMSSD) depressed (≤ 80% of baseline) |

- Resting = readings with `activity ∈ {rest, sleep}`. Baselines need ≥ ~14 days
  of history (iOS `minimumBaselineDays = 14`; backend requires ≥ 10 baseline rows
  in the 30d-but-not-last-7d window).
- **HRV = RMSSD** of successive RR-interval differences. iOS RR intervals are in
  **seconds** (×1000 → ms in the result); backend RR intervals are stored in
  **milliseconds**. Keep this unit difference in mind when comparing the two.
- iOS uses **deterministic warning IDs** (`stableID(for:)`, SHA-256 of a seed
  string) so a logical warning keeps its id across recomputes (stable deep links,
  no duplicate notifications). The backend uses random `uuidv4()` and guards
  re-firing with `hasUnresolved(...)` instead.

> **Client/server divergence is intentional but real.** The two engines don't
> produce byte-identical results (window sizes, consecutive-vs-count day logic,
> threshold representation, RR units, ID strategy all differ slightly). The
> backend is the recompute/authority for synced data; the iOS engine is for
> live/offline. If you change a rule, change it in **both** and update both test
> suites (`WarningsEngineTests.swift` and `tests/warningsEngine.test.ts`).

## Demo Mode

- Toggle in onboarding ("I don't have my device yet") or Settings; persists in
  `UserDefaults` key **`isDemoMode`**.
- `MockBLETransport` emits HR every 1 s and temperature every 5 s, with smoothed
  HR drift, circadian temp variation (±0.3 °C, peak ~18:00), and scenario-driven
  spikes. `DemoModeService.seedReadings(scenario:into:)` backfills ~35 days.
- Four scenarios, each engineered to fire a specific warning: **Normal Week**
  (none), **Overheating Workout** (→ OVERHEATING), **Getting Sick** (→
  GETTING_SICK), **Poor Recovery** (→ FATIGUE_RECOVERY). Switching a scenario
  clears prior `DEMO`/`"DEMO"` device readings, reseeds, and re-runs the engine.

## Deep links

Custom scheme `heartrate://` and Universal Links (`https://<domain>/...`) parse
to the same `AppRoute`:
`dashboard`, `history/hr|core|skin|hrv|eda`, `warnings/<uuid>`, `settings`, `pair`.
Test in simulator: `xcrun simctl openurl booted "heartrate://dashboard"`.
Universal Links require deploying the backend over HTTPS, editing
`HeartRate.entitlements` with the real domain, and setting `APPLE_TEAM_ID`.

## Conventions

- iOS: dependencies flow through `AppEnvironment`; keep `WarningsEngine` pure and
  SwiftData-free; new screens get an `AppRoute` case + router handling so they're
  deep-linkable. Localized strings live in `Resources/{en,nl}.lproj`.
- Backend: all setup through `buildServer()` so tests stay in-process via
  `inject()` (no real port/network). Remember `.js` import extensions in TS.
- The roadmap (`docs/ROADMAP.md`) is the "definition of done" checklist; the spec
  bans placeholders/stubs except the explicitly-marked **Garmin Health API**
  extension point (`SyncService.swift` stub; add a `/integrations/garmin` route
  group on the backend when implementing).

## Gotchas

- **Apple audience mismatch risk.** `APPLE_CLIENT_ID` defaults to `com.pulse.app`
  (checked against the token `aud`), but the iOS bundle id is `com.heartrate.app`.
  Set `APPLE_CLIENT_ID` to the real bundle id in the backend env or Apple Sign-In
  will reject tokens. (`APPLE_BUNDLE_ID` for the AASA file is separate.)
- **Seed data is time-relative.** Warnings depend on `Date.now()` windows
  (overheating 48 h on the backend / 24 h on iOS, baselines 7/30 days), so a stale
  DB stops firing warnings — re-run `npm run seed` / re-pick a demo scenario.
- The committed `backend/data/heartrate.db*` files are a seeded dev database, not
  a fixture the tests rely on (tests build their own DB via `buildServer`).
- Default `JWT_SECRET` is `dev_secret_change_me` — must be overridden in prod.
- **Upload wire format is exact.** `SyncService.ReadingPayload` must mirror the
  backend zod schema in `routes/readings.ts`: snake_case keys, **numeric Unix-ms**
  `timestamp`, RR intervals in **ms** (the model stores seconds), `temp_site1` =
  core / `temp_site2` = skin, and `activity` nil (not `"unknown"`). A mismatch
  here 400s every batch silently. (This was previously broken — keep them in
  lockstep; the round-trip is covered by `api.test.ts`.)
